# 04 开发日志与问题排查

按时间顺序记录工程演进：每个阶段做了什么、为什么这么选、遇到什么问题。

## 阶段一：工程搭建（9 月上旬）

- STM32CubeMX 建立 `CRTC_CAR_DEMO.ioc`，配置时钟树（HSE 8 MHz × PLL9 = 72 MHz）、GPIO、TIM2/TIM3、SPI1；
- 选 **CMake + Ninja** 而非 IDE 工程，保证任何机器拉下代码即可命令行编译；
- 建立分层目录：`Core/`（HAL 初始化）、`Chassis/`（电机控制 + 运动学解算）、`PS2/`（手柄驱动）、`cmake/`（构建目标）。

选 C + C++ 混合，是因为 HAL 与 CubeMX 生成 C 代码，而电机、手柄这类有状态外设用类封装更清晰（构造时绑定定时器与通道，不必到处传句柄）；通过 `extern "C"` 导出 `chassis_init()` / `chassis_move()` / `PS2_Init()`，两侧互不干扰。

## 阶段二：电机与底盘驱动（9 月中旬）

- 实现 `Motor` 类（PWM 通道 + 方向控制，封装正反转与限幅）与 `ChassisCtrl`（四电机运动学，初版差速、后改麦轮）；
- 编译通过，占用 RAM 1920 B / FLASH 15496 B。此时**代码从未在实物上验证**，引脚沿用了通用开发板的习惯。

## 阶段三：实物联调与引脚纠偏（10 月 17 日）

### 问题一：构建缓存被 IDE 污染

CLion 用自己的 MinGW 工具链重新 configure，`build/Debug/CMakeCache.txt` 里写满 `E:/CLion 2026.2.2/bin/mingw` 路径，导致 `arm-none-eabi-gcc` 构建直接失败。

**解决**：废弃被污染的缓存，显式指定工具链文件与 Ninja 重新配置。经验是交叉编译工程的构建目录与工具链强绑定，被 IDE 的本地编译器碰过之后删掉重建最省事。

### 问题二：ST-LINK 连不上，报 `Unable to get core ID`

CLI 报 `Voltage : 0.00V` 或 `1.36V`，且多次尝试间随机跳变（0.00 / 0.49 / 1.36 / 1.37），从未到 3.3 V。

**排查**：先后试了 `mode=UR`、`mode=hotplug`、把 `freq` 从 4 MHz 降到 100 kHz，现象完全一致，排除时序问题；电压读数不稳定说明不是软件问题；换用另一只 ST-LINK 并确认目标板供电后读到 `3.09V`，一次连接成功。

**结论**：`Voltage` 是 ST-LINK 从目标板 VREF 引脚实测的电压，STM32F103 最低工作电压 2.0 V。显示 0.00 V 或 1.x V 且随机跳变时，说明目标板未正常供电或 SWD 地线未导通，调连接参数不可能连上。

### 问题三：四轮不转 —— 引脚与 PCB 完全错位

逐脚核对原理图后发现原固件的三组功能全部对不上：

| 原固件使用 | 板上实际功能 |
| --- | --- |
| TIM2 → PA0~PA3 | 空脚 |
| TIM3 → PA6/PA7 | PS2 的 CS / CLK |
| TIM3 → PB0/PB1 | STBY1 / STBY2 |
| SPI1 重映射 → PB3~PB6 | 空脚 |
| — | 电机实际接 PA8~PA11（IN1）、PB12~PB15（IN2） |

**解决**：板级初始化从 `tim.c` 剥离到 `Chassis.cpp`——TIM1 CH1~CH4 输出 PWM 到 PA8~PA11，PB12~PB15 做方向，PB0/PB1 拉高使能，同时停用 `MX_TIM2_Init` / `MX_TIM3_Init` / `MX_SPI1_Init`。

**代价**：`.ioc` 未同步，此后不能用 CubeMX 重新生成代码，属当前技术债。

### 问题四：`_m[4]` 数组越界

`ChassisCtrl` 的成员是 `Motor _m[4]`，构造函数却写成 `_m[4] = Motor(...)`。合法下标只有 0~3，这一行是未定义行为：数据写到对象之后的内存，真正的 `_m[3]` 保持空指针，第四只电机一调用 `set_speed()` 就解引用空 `TIM_HandleTypeDef*` 触发 HardFault。修正为 `_m[3]`。

### 问题五：左右轮分组错误

初版差速解算把 FL+FR 归为「左」、BL+BR 归为「右」，实际应为 **FL+BL 为左、FR+BR 为右**。直线时看不出问题，一旦差速转向前后轮就打架。

## 阶段四：验证与文档（10 月 17 日）

- 修正引脚后烧录成功，四轮满占空比同向转动，录制 `docs/media/chassis-motion.mp4`；
- 按手册 4.3 规范整理文档体系，全部放入 `docs/`。

## 阶段五：切换为麦轮运动学（10 月 18 日）

确认整车装配的是**麦克纳姆轮**后，差速解算不再适用——差速只能前进与转向，无法横移。

- 新增 `ChassisCtrl::update_mecanum(vx, vy, w)`，按 X 型辊子布局做逆运动学：

  ```
  FL = vx - vy - w      FR = vx + vy + w
  BL = vx + vy - w      BR = vx - vy + w
  ```

- 加入**等比缩放**：斜向移动时单轮合成速度可能超过 ±3600，直接截断会破坏四轮比例导致走斜，改为按最大值等比压缩、方向不变；
- 主循环改为 **前 → 后 → 左 → 右** 固定序列轮播，每方向 3 秒、间隔 5 秒，用于验证横移是否成立；
- 保留原 `update(v, turn)` 差速接口作备用，底层 `Motor` 不变。

用固定序列而不是随机动作，是因为演示需要可复现、可剪辑，固定 4 步循环也方便逐帧核对麦轮转向。

**待验证**：横移方向取决于辊子安装朝向，若实测相反，只需把 `update_mecanum()` 中 `vy` 的符号取反。

## 阶段六：接入 PS2 手柄遥控（10 月 18 日）

轮播验证通过后，把手柄输入接上来替换固定序列。

- **驱动改写**：原 `PS2` 类基于硬件 SPI 且用 SPI1 重映射的 PB3~PB6，与板上接线完全不符；改为 GPIO 翻转模拟时序，引脚 PA4~PA7；
- **时序参数**：CLK 空闲高电平、LSB 先行、半周期 3 μs（约 166 kHz）、字节间隔 30 μs、CS 全程拉低；
- **模拟模式握手**：上电 300 ms 后发送 `01 43 00 01 00…` → `01 44 00 01 03…` → `01 43 00 00 5A…`，否则手柄只回数字模式、摇杆字节恒为 `0xFF`；
- **在线检测**：校验模式字节（0x41 / 0x73 / 0x79），非法即返回失败，修复了原实现恒返回 `true` 的缺陷；
- **掉线保护**：连续 5 次读失败输出零速度；
- **摇杆映射**：左摇杆 = 平移（前后 + 横移），右摇杆 X = 旋转；±12 死区；旋转降半速。

**为什么先做轮播再接手柄**：轮播时运动学与电机是唯一变量，异常能直接归因到解算；接上手柄后变量变成两个（运动学 + 通信），方向不对时很难判断是公式错还是读到错帧。先把已知正确的部分锁死、再叠加新变量，是这次调试最省时间的一个决定。

## 阶段七：加入舵机（10 月 18 日）

在 PB9 上增加一路舵机输出，用手柄「×」键切换位置，为后续收集机构做准备（细节见文档 [05](./05-舵机机构.md)）。

- **时基**：TIM4，PSC = 71、ARR = 19999 → 1 MHz 计数、20 ms 周期，CCR 数值即脉宽微秒数；
- **引脚**：PB9 = TIM4_CH4，无需重映射，与电机 PA8~PA11、PS2 PA4~PA7 均不冲突；
- **按键**：上升沿检测，一次按压只切换一次（50 Hz 下按住会被读到几十次）；
- **角度**：上电 90° 中位，在 30° / 150° 间往复，避开机械极限。

舵机单独用 TIM4，是因为 50 Hz 与电机 20 kHz 的预分频、重装值差两个数量级，共用会互相牵制；分开后调电机频率不影响舵机脉宽，也不占 CPU。
