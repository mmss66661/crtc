# 04 开发日志与问题排查

按时间顺序记录工程演进。每个阶段写清「做了什么 / 为什么这么选 / 遇到什么问题」。

## 阶段一：工程搭建（9 月上旬）

- 用 STM32CubeMX 建立工程 `CRTC_CAR_DEMO.ioc`，配置时钟树（HSE 8 MHz × PLL9 = 72 MHz）、GPIO、TIM2/TIM3、SPI1；
- 选择 **CMake + Ninja** 作为构建系统（而非 IDE 工程），保证任何一台机器拉下代码就能命令行编译；
- 建立目录分层：

```
Core/       CubeMX 生成的 HAL 初始化
Chassis/    底盘：电机控制类 + 差速解算（后续承载板级初始化）
PS2/        PS2 手柄驱动（C++ 类 + extern "C" 包装，便于在 C 的 main.c 中调用）
cmake/      CubeMX 生成的构建目标
```

**为什么用 C + C++ 混合**：HAL 库和 CubeMX 生成的是 C 代码，而电机、手柄这类有状态的外设用类封装更清晰（构造时绑定定时器与通道，避免到处传句柄）。通过 `extern "C"` 导出 `chassis_init()` / `update()` / `PS2_Init()` 等 C 接口，两侧互不干扰。

## 阶段二：电机与底盘驱动（9 月中旬）

- 实现 `Motor` 类：两个 PWM 通道 + 方向控制，封装正反转与限幅；
- 实现 `ChassisCtrl`：四电机差速解算；
- 编译通过，占用 RAM 1920 B / FLASH 15496 B。

此时**代码从未在实物上验证过**，引脚配置完全沿用了通用开发板的习惯。

## 阶段三：实物联调与引脚纠偏（10 月 17 日）

### 问题一：构建缓存被 IDE 污染

CLion 打开工程时用自己的 MinGW 工具链重新 configure，`build/Debug/CMakeCache.txt` 里写满了 `E:/CLion 2026.2.2/bin/mingw` 的路径，导致用 `arm-none-eabi-gcc` 构建时直接失败。

**解决**：废弃被污染的缓存目录，明确指定工具链文件与 Ninja 路径重新配置：

```bash
cmake -S . -B build/Debug -G Ninja \
      -DCMAKE_BUILD_TYPE=Debug \
      -DCMAKE_TOOLCHAIN_FILE=cmake/gcc-arm-none-eabi.cmake
```

**经验**：交叉编译工程的构建目录与工具链强绑定，被 IDE 的本地编译器碰过之后最省事的做法是删掉重建，而不是试图修补缓存。

### 问题二：ST-LINK 连不上，报 `Unable to get core ID`

连续多次尝试，CLI 报 `Voltage : 0.00V` 或 `1.36V`，且数值在不同次尝试间随机跳变（0.00 / 0.49 / 1.36 / 1.37），始终到不了 3.3 V。

**排查过程**：

1. 先怀疑连接模式，依次试了 `mode=UR`（复位下连接）、`mode=hotplug`、`freq` 从 4 MHz 降到 100 kHz——现象完全一致，排除时序问题；
2. 注意到电压读数不稳定且从未达到 3.3 V，判断不是软件问题；
3. 换用另一只 ST-LINK 并确认目标板供电后，`Voltage : 3.09V`，一次连接成功。

**结论**：`Voltage` 是 ST-LINK 从目标板 VREF 引脚实测的电压，STM32F103 最低工作电压 2.0 V。当它显示 0.00 V 或 1.x V 且随机跳变时，说明目标板没有正常供电或 SWD 地线未导通，无论怎么调连接参数都不可能连上。这条经验后来写进了根目录 README 的烧录排障小节。

### 问题三：四轮不转 —— 引脚与 PCB 完全错位

拿到 PCB 原理图逐脚核对后，发现原固件的三组功能全部对不上：

| 原固件使用 | 板上实际功能 |
| --- | --- |
| TIM2 → PA0~PA3 | 空脚 |
| TIM3 → PA6/PA7 | PS2 的 CS / CLK |
| TIM3 → PB0/PB1 | STBY1 / STBY2 |
| SPI1 重映射 → PB3~PB6 | 空脚 |
| — | 电机实际接 PA8~PA11（IN1）、PB12~PB15（IN2） |

**解决**：把板级初始化从 CubeMX 生成的 `tim.c` 中剥离，改由 `Chassis.cpp` 自行完成——TIM1 CH1~CH4 输出 PWM 到 PA8~PA11，PB12~PB15 做方向，PB0/PB1 拉高使能。同时停用 `MX_TIM2_Init` / `MX_TIM3_Init` / `MX_SPI1_Init`。

**代价与约定**：`.ioc` 文件未同步修改，此后**不能用 CubeMX 重新生成代码**，否则会覆盖上述修正。这是当前的已知技术债，长期看应当在 CubeMX 中按新引脚重新配置一次并替换掉手工初始化。

### 问题四：`_m[4]` 数组越界

`ChassisCtrl` 的成员是 `Motor _m[4]`，构造函数却写成了 `_m[4] = Motor(...)`。合法下标只有 0~3，这一行属于未定义行为：数据被写到对象之后的内存，而真正的 `_m[3]` 保持默认构造的空指针。

后果是第四只电机一旦 `set_speed()` 就会解引用空 `TIM_HandleTypeDef*`，触发 HardFault。编译器不会报错、运行时也不一定立刻崩，属于典型的静默错误。修正为 `_m[3]` 即可。

### 问题五：左右轮分组错误

初版把 FL + FR 归为「左」、BL + BR 归为「右」，实际应当是 **FL + BL 为左、FR + BR 为右**。直线行驶时看不出问题（四轮速度相同），一旦差速转向就会前后轮打架。已修正。
